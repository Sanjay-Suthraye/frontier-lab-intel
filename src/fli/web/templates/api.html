JSON API

For BIT's Signals & Alerts platform layer. Times are UTC ISO 8601 with a trailing Z. relevance is a calibrated probability in [0, 1] that the audience would call the development worth knowing (not that it is material; p_material is the same number under its old name). It comes from the live scoring model; model_version prior-v0 marks the unvalidated hand-set prior. Machine-readable schema: /api/openapi.json.

Read endpoints

EndpointParametersReturns
GET /api/developments audience investment | ai_team (omit: both, ranked by the higher score) · since ISO date on first_seen_at (default: last 7 days) · updated_since for pollers (catches re-scored or grown items) · min_p 0–1 · lab · event_type · limit ≤ 500 ranked items with scores, both lenses, tickers (exposure exactly as the alert rules count it, with BIT weights; basis lens = a direction the investment lens commits to, event = an event-specific exposure link), held_tickers (the BIT holdings among them), lab_relations (the lab's curated relations: context, never exposure), source classes, unconfirmed, alerts and cited sources (curated: true marks a curated register entry, with the cited_url it cites; never an official source)
GET /api/developments/{id}– full detail: insights with evidence quotes and verified marks, score contributions, exposure links (each with basis event | lab_relation | below_threshold), alerts, labels, and why_flagged per audience: the materiality decision (severity, rule_severity, unconfirmed), rules that fired with the facts each matched, guards, not_fired rules with their first failed condition, the facts and the score the rules read with its top contributions
GET /api/alerts audience · since (default: last 7 days) · severity P1 | P2 | P3 · status open | acked | suppressed | all (default all) · limit ≤ 1000 alerts newest first with fired rules, delivery state (delivery.channels in_app / slack, delivery.mode live | historical) and a link to the development; for routing: relevance, the alert audience's lens action and horizon, tickers [{symbol, direction, bit_weight, basis}] and held_tickers, the exposure and BIT holdings exactly as the materiality rules count them (event-specific exposure links, and the tickers a non-abstaining investment lens gives a positive / negative / mixed direction), lab_relations (context only, never routing) and why_flagged (the decision for the alert's audience evaluated now, same shape as on /api/developments/{id})

GET /api/health–ok | degraded | critical, source states, last ingest, open ops events, spend vs budget

Write endpoints

Protected by HTTP Basic auth when FLI_BASIC_AUTH=user:pass is set (FLI_AUTH_ALL=1 protects every page too); labels and acks are then recorded under the authenticated login, whatever the body says. Without credentials configured only a local client (loopback, not through a proxy) may write; everyone else gets 403. Cross-origin browser posts are rejected.

EndpointBody (JSON or form)
POST /api/labels{"development_id": 12, "audience": "investment", "label": 2, "annotator": "anna", "reason": "..."} — label 0 noise · 1 worth knowing · 2 material; stored as human:<login> under auth (else human:<annotator>), rubric r1; re-posting replaces your earlier label
POST /api/alerts/{id}/ack{"status": "acked"} (or open / suppressed)

Examples

curl -s '{{ base }}/api/developments?audience=investment&min_p=0.6&since=2026-10-27'
curl -s '{{ base }}/api/alerts?severity=P1&status=open'
